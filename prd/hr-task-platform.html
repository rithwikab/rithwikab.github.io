Problem

HR operations teams handle a steady stream of requests: onboarding steps, document requests, access, policy questions. They arrive unstructured, often by email or chat, and someone has to read each one, decide what it is and pass it on.

  • Triage eats time. Categorising requests by hand is repetitive and slow.
  • Onboarding steps get missed. Without a fixed sequence, new joiners have different first weeks.
  • Ownership is unclear. People aren’t sure what’s assigned to them, and managers can’t see what’s stuck.

Insight

Categorising a request is exactly the kind of judgement a language model does well and cheaply. Deciding what happens to a person is not. So the AI labels the work, and people own every decision after that.

Goals and non-goals

Goals

  1. Cut manual triage by categorising new tasks automatically.
  2. Make onboarding a repeatable workflow.
  3. Make it obvious to everyone what’s assigned to them.
  4. Never let an AI outage stop work.

Not in v1

  • Payroll, leave or a full HR system of record
  • AI making decisions about people
  • A chat assistant for employees

Key decisions and trade-offs

AI labels, people decide
The model only suggests a category. Assignment and anything that affects an employee stays with a person. Trade-off: less automation than possible, in exchange for trust in a sensitive domain.
Structured output instead of free text
The model has to answer in a fixed format with a category from a known list. That makes results predictable and easy to validate. Trade-off: adding a new category means updating the list.
Fallback instead of failure
If the AI call fails or times out, the task still goes through without the automatic label, so work continues. Trade-off: some tasks need manual categorisation during an outage.
Classify once, at creation
Each task is sent to the model once, which keeps cost predictable and latency out of every other screen.

Technical design

FrontendExpress API · JWT + RBACMongoDBOpenAI (structured output)Category saved on task
  • API layer: Node.js and Express, with JWT sessions and role checks on every route.
  • Classification: on task creation, the task text is sent to OpenAI with a fixed output format. The returned category is validated before it’s saved.
  • Fallback: classification failures are caught and handled asynchronously, so saving the task never depends on the AI call.
  • Data: users, tasks, onboarding workflows and notifications live in MongoDB.
  • Screens: dashboard, task list, assigned tasks, create task, notifications, user registration.

Risks and mitigations

Personal data is sent to a third-party modelSend only the task text needed to categorise it. Planned: strip names and IDs before the call.
AI costs grow with task volumeClassify each task once, at creation, never on every view.
The AI service is downFallback path keeps tasks flowing without the label.
