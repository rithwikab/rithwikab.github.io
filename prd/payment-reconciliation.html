Problem

Reconciliation means confirming that every payment in one set of records has a matching entry in another. In many finance teams it still happens in spreadsheets, and it breaks in three predictable ways:

  • It doesn’t scale. Effort grows with volume, so month-end turns into a backlog.
  • Re-uploads corrupt the totals. Uploading the same file twice, or retrying a failed import, creates duplicate records that throw every figure off.
  • There’s no trail. When an auditor asks who changed a record and when, the answer lives in someone’s memory.

I saw this class of problem from the finance side, through my PGDM in Finance & Analytics and my internship at Oxane Partners, before building the fix as an engineer.

Insight

Matching the easy records isn’t the hard part. Trusting the result is. So this product bets on trust: re-uploads that are always safe, a clear list of exceptions, and a full audit trail. It does not bet on a clever matching algorithm.

Goals and non-goals

Goals

  1. Reconcile a typical batch in seconds, so analysts never wait on a spinner.
  2. Make ingestion safe to repeat: uploading the same file twice changes nothing.
  3. Trace every change to a person and a time.

Not in v1

  • Automatically resolving mismatches
  • Direct bank or payment-gateway integrations
  • Multi-currency and FX handling
  • Fuzzy or ML-based matching

Keeping v1 narrow meant the trust features (idempotency, audit, access control) could be built properly, not bolted on later.

User flow

  1. The analyst uploads a payment file and gets a run ID straight away.
  2. The file is queued. A background worker fingerprints each record and skips any it has seen before.
  3. New records are matched and the results are saved against the run.
  4. The dashboard updates with matched, unmatched and flagged counts.
  5. The analyst reviews the exceptions. The manager checks the summary and signs off.
  6. Every step above is written to the audit log.

Key decisions and trade-offs

Background queue instead of processing in the request
Big files would time out a normal web request. Moving work to a BullMQ queue keeps uploads instant. Trade-off: it needs Redis, and the interface has to show job status.
Fingerprint every record instead of trusting source IDs
Files from different sources don’t share reliable IDs, so each record gets a deterministic hash of its identifying fields. The same record always produces the same hash, which makes duplicates easy to reject. Trade-off: two genuinely different payments with identical fields would collide, so the hashed fields have to be chosen carefully.
Audit log from day one
An append-only log is cheap to build early and expensive to retrofit. It also turned out to be the fastest way to debug my own test runs.
MongoDB for storage
Payment files vary in shape by source, and a document store absorbs that without migrations. Trade-off: fewer relational guarantees, so uniqueness is enforced on the hash itself.

Technical design

ClientExpress API · JWT + RBACBullMQ queue (Redis)Worker: hash, dedupe, matchMongoDB
  • API layer: Node.js and Express. Every route checks a JWT and then the user’s role before doing anything.
  • Ingestion: uploads are accepted and queued at once. Workers process records asynchronously and can retry safely because ingestion is idempotent.
  • Idempotency: a deterministic hash per record acts as its key. A record whose hash already exists is skipped, not inserted again.
  • Data: records, runs, users and the audit log live in MongoDB.
  • Deployment: Docker for a consistent build, hosted on Render.

Risks and mitigations

Very large files strain memoryPlanned: stream-parse uploads in chunks instead of loading the whole file.
A role is set up with too much accessNew users start with the least access, and only admins can change roles.

What’s next

  1. Exception workflow: assign, comment on and resolve each mismatch, all captured in the audit log.
  2. Tolerance matching: match amounts and dates within a configurable tolerance, with the reason shown.
  3. Connectors: pull statements from banks and payment gateways instead of uploading files.
  4. A pilot: put it in front of a small finance team and instrument the two “track in pilot” metrics.
